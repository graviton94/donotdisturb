# 14 · 출시 후 업데이트 로드맵

출시본은 **앱 60종 · 10티어 · 마지막 앱 약 12주**로 확정한다(04 경제 9장). 빠진 대형 앱은 출시 후 업데이트로 **위에 쌓는다**.

## 1. 원칙

| 원칙 | 이유 |
|---|---|
| **새 콘텐츠는 맨 위에** (새 티어·새 환생 층) | 초반 곡선과 기존 저장 데이터가 흔들리지 않는다. 영향은 끝까지 간 플레이어에게만 간다 |
| 중간 티어에 끼워 넣지 않는다 | 출시 후 중간 삽입은 해금 순서·가격·시너지 칸을 모두 바꾼다. 중간 교체가 필요하면 **출시 전에** 한다 |
| 공식은 그대로, 콘텐츠로 맞춘다 | 티어 ×6, 레벨 곡선, 클라우드 공식이 위로 그대로 이어진다. 도착 시점은 해금 레벨 배치로 맞춘다 |
| 업데이트마다 시뮬레이션 검증 | `gradle -p tools/economy-sim run --args="update <출시일수> <추가일수> <시드> <팩>"`: 12주 차 저장에 팩을 켜고 이어서 플레이 |
| 업데이트 하나 = 6종 한 티어 + 이벤트 | 6종이 권역 × 기능 히트맵에서 한 줄을 이룬다. 출시 이벤트(복귀 보상, 한정 꾸미기)와 묶는다 |

## 2. 엔진 지원 (완료)

- `Catalog.packs`: 콘텐츠 팩을 켜고 끈다. 게임은 콘텐츠 버전에 맞춰 설정, 시뮬레이터는 중간에 켠다.
- `ContentPack.AiTier`: 업데이트 1의 초안(아래). 테스트 `contentPacksAddTiersOnTopWithoutTouchingLaunchContent`가 "출시 콘텐츠는 그대로, 새 티어는 위에"를 지킨다.
- 시뮬레이터 `update` 모드: 적용 시점 레벨, 11티어 첫 앱, 팩 마지막 앱 도착일, 주별 최고 레벨, 적용 후 동기화 횟수.

## 4. 업데이트 체크리스트

1. 팩 데이터(`Content.kt` packApps), 아이콘(코드 또는 발주), 문구(`docs/content/app-texts.json`).
2. 시뮬레이터 `update` 모드 시드 8: 적용 후 성장이 다시 붙는지, 팩 마지막 앱이 목표 기간(예: 4~6주) 안인지, 폭주(GB ×4/동기화 같은)가 없는지.
3. 카탈로그 재생성·재발행, 05 참조표 재생성, 결정 기록.
4. 저장 데이터 이전: 팩 앱이 없던 저장은 그대로 읽힌다(새 앱은 해금 레벨에 닿으면 상점에 나타남).

**교훈** · 업데이트에는 새 티어(콘텐츠)와 **새 성장 축**이 함께 있어야 한다. 성장 축은 이미 쌓인 재화로 한 번에 살 수 없게, 업데이트 이후의 **플레이 행동(초기화)**에 묶는다.

## 6. 기간 한정 팩

v1.6은 `LiveEvent` 카탈로그에 연쇄 주간과 아시아권 시너지 주간을 추가한다. 콘텐츠 버전의 영구 `Catalog.packs`와 별개로 세션마다 설정한 UTC 창을 확인한다. 활성 창은 한 개, 최대 7일이다. 기간이 끝나면 직접 지급 P 가산이 종료된다. 일일 도전 기록과 최근 수입을 사용하는 오프라인 산정에는 이벤트 가산이 전해지지 않는다. [운영 설정](../balance/remote-tuning.md) · [화면 계약](../balance/api-changes.md#v16-도감주간-지급기간-한정-콘텐츠)
